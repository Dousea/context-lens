# context-lens Agent Guide

## What this is

A Claude Code plugin (a mod) that draws a band above the prompt: it sets the reasoning effort for each prompt, picks the model with the prompt cache in mind, and shows the cache timers, context window and rate limits. It is a fork of [HeyCubit/effortless](https://github.com/HeyCubit/effortless) 1.71.0 (MIT); the fork's history starts from one squashed import of it, so upstream changes are carried over by hand, not merged.

## Layout

- `hooks/register.tsx`: the entry module. It resets the per-load state, reads the settings and calls each `register…Hooks(on)`.
- `hooks/handlers/`: the hooks, a file per group of events: `session`, `turn`, `commands`, `prompt`, `agents`, `footer` (the desktop footer and the reply footers) and `above-prompt`, which picks the band to draw.
- `hooks/render/`: what is drawn above the prompt: the terminal band, the dashboard, the alert bands, the effort rows, the lens row, the settings panel, the compact and handoff bars, the handoff card and the setup guide.
- `hooks/logic/`: what the mod does, a module per domain: `judge`, `bench`, `switching` (model switches and offers), `effort`, `spend`, `cache`, `alerts` (swamp and hot), `handoff`, `compact`, `subagents`, `lens`, `settings`, `setup`, `timers`.
- `hooks/svg/`: the inline SVG: the band scenes, controls, glows, the art, the brand mark and the thinking dots.
- `hooks/core/`: what every layer shares: constants, the palette, the config, session state, env and the debug log.
- `hooks/model.ts`: cache-clock, re-cache and context-bar arithmetic, with no host calls.
- `hooks/theme.ts`: the theme and the light look.

Imports go one way: `core` → `svg` → `logic` → `render` → `handlers` → `register.tsx`. A constant shared by modules of different domains lives in `core/constants.ts`; one used by a single module lives in it.

- `tests/`: `context-lens.test.ts` (the mod through the host's test harness), `model.test.ts`, `lens.test.ts`.
- `commands/context-lens.md`: the `/context-lens` command file.
- `bench/`: judge and helper benchmarks with their results.
- `.claude-plugin/`: `plugin.json` and `marketplace.json`. `.claude-plugin/types/` is generated by the host and gitignored.

For the mod API (`$`, `on(...)`, `ui.render`, state, timers), load the `plugin-authoring` skill rather than guessing.

## Checks

- `claude plugin test .` runs every test. All pass; there are no known failures, so any failure is yours.
- `claude plugin validate .` checks the manifest and marketplace.
- `npm run format` formats the repo with Prettier (`npm install` first); `npm run format:check` reports files that are not formatted.
- Try a change live with `CONTEXT_LENS_LOG=<file> claude --plugin-dir <repo or worktree path>`. A `--plugin-dir` copy replaces the installed `context-lens@context-lens` for that session. `/context-lens debug` shows the state, and `/reload-plugins` reloads the installed copy, not the working tree.

## Host traps

- The host denies a state write made while `ui.render` is being dispatched (`state.set: denied … while ui.render is being dispatched`). Defer it with `$.clock.after(0, …)` and draw from a local value meanwhile.
- `/model` persists as the app's default. A switch that should last only for the session changes the request's model instead.
- A `$.clock.now()` per request in the `send` path made the cache-countdown tests time out; reuse `cacheExpires`.
- Outside `register.tsx`, a function that takes `$` must be a `function` declaration. Past an import the host follows `$` only into one, and an arrow stops the module from loading (`$ is passed to "x", a name bound to a function expression`).
- The host reads an atom only from a `const` of the file that calls `read` or `update` on it. Each file that uses an atom declares it, with the same key and initial value; the contract in `types/index.d.ts` holds its type.
- An imported `let` can be read but not assigned. A module whose `let` another module writes exports a `setX` beside it.

## Git and releases

- `main` is what the `Dousea/context-lens` marketplace serves, and a fresh install copies its tip whatever the version says, so `main` must always be releasable. Work on a branch (`feat/…`, `fix/…`, `docs/…`) and merge when it is ready.
- Bump `version` in `.claude-plugin/plugin.json` only when releasing, never per commit: semver, and below 1.0 a patch for fixes and a minor for features. Installs update when the version differs, not only when it rises.
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): description` in the imperative, subject at most 72 characters, details in the body. Scopes in use: `band`, `footer`, `judge`, `model`, `settings`. No version prefixes and no AI attribution.

## Naming: Prefer full, descriptive names

Name variables, functions, parameters, etc. with full, descriptive words by default. Avoid single letters or abbreviations unless they are genuinely necessary (e.g. a well-established convention). In this codebase the mod API's own names count as convention: `$` for the engine, `e` for the event and `next` in handlers. Existing short names elsewhere are not a reason to add more; rename one only when you are already changing that code.

## Variables: Inline what is used once

Don't declare a variable for a value used exactly once — inline it at the call site. Justified exceptions: naming clarifies intent (an unclear condition, magic number, or expression), extracting avoids a deeply nested or overlong expression, or TypeScript needs the binding (const assertions, type narrowing, discriminated unions). If none apply, inline it.

## Comments: Only when the code cannot explain itself

Do not add comments that restate what the code already says. Write a comment only to explain something the code cannot convey on its own — a non-obvious "why", a workaround for a host constraint, a subtle edge case, or an intentional deviation from the expected. If reading the code makes the intent clear, leave the comment out.

Never write a comment as a postmortem of how the code got here — what it used to do, what was changed or fixed, or which migration it's mid-way through (e.g. "no longer needed", "originally this called X"). That history belongs in the commit message, not the source, and it rots as the surrounding code moves on. State only the present-tense invariant or constraint a reader needs right now.

## Whitespace: Group code into visual paragraphs

Separate the distinct steps of a block with blank lines, the way paragraphs separate ideas in prose. A reader should be able to see the seams — _set up_, _decide_, _act_ — without parsing the logic first. Dense runs of statements with no breathing room are hard to read even when each line is simple.

- Insert a blank line between logical phases: computing a value, branching on it, and each independent side effect.
- Keep tightly-coupled lines together (a value and the guard on it, a guard and its early return) with no blank line between them — grouping is meaningful in both directions.
- One state update / one concern per visual paragraph. If a block does three things, show three groups.
- Prettier keeps blank lines but never adds them, so the grouping is yours to write. Apply this to code you write or change; don't regroup untouched code, since a whitespace-only diff buries the real change.

```tsx
// Cramped: computing the expiry, saving it and redrawing run together
const now = await $.clock.now()
lastResponseAt = now - r.seconds_since_last_response * 1000
const left = lastResponseAt + CACHE_TTL[cacheTtl]
cacheExpires = r.prompt_cache_likely_expired || left <= now ? now - 1 : left
await rememberCache($)
await checkSwamp($).catch(() => undefined)
await showCache($).catch(() => undefined)
$.ui.invalidate('ui.render')
redrawSoon()
```

```tsx
// Grouped: compute · persist and check · redraw each read as separate paragraphs
const now = await $.clock.now()
```

## Style that already holds

Prettier (`.prettierrc.json`) sets the layout: no semicolons, single quotes, two-space indent, lines up to 120 characters. Run `npm run format` before committing. Beyond that, match the surrounding code, such as arrow functions for small helpers.
